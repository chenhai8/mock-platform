# MockLab Linux Docker 部署教程

本文只部署业务容器 app 和 runner。数据库使用现有 MySQL 5.7，反向代理使用现有 Nginx，不启动数据库或 Nginx 容器。前端构建为 `dist/` 后放入现有 Nginx webroot；现有 Nginx 负责前端静态资源和反向代理后端接口。

## 1. 部署形态

```text
使用者 / 业务服务器 -> 现有 Nginx
                        ├── 前端静态目录 dist/
                        ├── /api、/m/、/actuator -> 宿主机 APP_PORT -> app:8080 -> 现有 MySQL 5.7
                        └── Unix Socket -> runner
```

- Compose 创建 app、runner 及 runner-socket 卷，不创建数据库或 Nginx 容器
- app 提供 `/api` 管理接口、`/m/` Mock 入口和 `/actuator`，不再提供前端静态页面
- 现有 Nginx 提供前端静态页面，并将 `/api`、`/m/`、`/actuator` 反向代理到 app 宿主机端口
- runner 不暴露网络端口，通过 Unix Socket 与 app 通信
- 访问入口沿用现有 Nginx 的域名、TLS 和管理访问控制；应用容器内部保持 HTTP

## 2. 服务器准备

建议先用 x86_64 Linux、4 核、8 GiB 内存和至少 10 GiB 可用磁盘验证。安装 Docker Engine 与 Compose v2 插件。目标是 ARM64 时，联网构建机器也要构建对应平台镜像，不能直接复制 x86 镜像使用。

```sh
docker version
docker compose version
```

将项目放到例如 `/opt/mocklab`，所有命令都在包含 `compose.yml` 的部署目录执行。

```sh
cd /opt/mocklab
# 仅在尚无 .env 时创建；已有配置直接编辑，不覆盖
if [ ! -e .env ]; then cp deploy/env.example .env; fi
chmod 600 .env
```

编辑 `.env`：

```dotenv
DB_URL=jdbc:mysql://192.168.10.30:3306/mocklab?useUnicode=true&characterEncoding=UTF-8&serverTimezone=UTC&useSSL=false
DB_USER=填写已有数据库账号
DB_PASSWORD=填写已有数据库密码
DB_INIT_MODE=always
APP_BIND=127.0.0.1
APP_PORT=16080
LOG_DAYS=7
LOG_MAX_ROWS=1000000
LOG_BODY=false
```

DB_URL 指向已有数据库；容器内 127.0.0.1 是 app 自身，不能将其作为宿主数据库地址。请 DBA 提供独立库和应用账号，账号授权沿用现有数据库管理流程。库不存在时可由 DBA 执行 deploy/init-mysql.sql。

DB_INIT_MODE=always 会在启动时执行 schema.sql 创建缺失的表，需 CREATE、REFERENCES 权限。如果 DBA 已手动执行建表脚本，设置为 never，应用仅需正常读写权限。

### 构建前端 dist

在宿主机构建前端：

```sh
cd frontend
npm ci
VITE_BACKEND_URL= npm run build
```

构建产物输出到项目根目录 `dist/`。将 `dist/` 复制到现有 Nginx webroot，例如 `/usr/share/nginx/html/mocklab/`，并确保 Nginx worker 用户可读取。

`VITE_BACKEND_URL` 留空时，前端调用浏览器当前 origin 的 `/api`、`/m` 路径，由现有 Nginx 分发到静态目录和后端 app。需要固定跨域或独立入口时，在 `frontend/.env.production` 填写浏览器可访问地址后重新构建。

### 接入现有 Nginx

将 `deploy/nginx.conf` 的 location 参考片段合入现有站点 server 内，保留现有域名、TLS 和访问控制。

- 静态资源目录按实际 webroot 修改 `root`，例如 `/usr/share/nginx/html/mocklab`
- 同机 Nginx：`proxy_pass http://127.0.0.1:16080;`
- 远程 Nginx：`proxy_pass http://业务服务器内网IP:APP_PORT;`
- 推荐将页面、`/api`、`/m/` 接入同一入口；只开放 Mock 调用时单独代理 `/m/`

## 3. 联网构建与启动

```sh
docker compose config --quiet
docker compose build
docker compose up -d
docker compose ps
```

首次构建需要下载公共基础镜像、Maven 依赖。运行阶段不访问这些仓库。执行服务要预热 4 个进程，首次就绪可能需要几十秒；后端等待 runner 健康后启动，再连接已有数据库；数据库地址和授权需要预先可用。

```sh
curl -f http://127.0.0.1:16080/actuator/health
docker compose logs --tail=100 app runner
```

健康结果应为 `{"status":"UP"}`。浏览器打开现有 Nginx 管理入口，创建第三方系统和接口，调试并发布。

## 4. 第一次真实调用

假设创建系统标识 `erp`，接口为 POST `/api/orders/query`，发布原样响应 `{"code":"0000","message":"成功"}`：

```sh
curl -i 'http://mock.company.internal/m/erp/api/orders/query' \
  -H 'Content-Type: application/json' \
  --data '{"orderId":"1001"}'
```

返回 HTTP 200，正文就是保存的文本。之后改为 JavaScript：

```javascript
function main(request, mock) {
  return {
    status: 200,
    body: {
      code: "0000",
      orderId: request.body.orderId,
      requestId: mock.uuid()
    }
  };
}
```

保存草稿后真实调用保持旧响应，重新发布后才切换到脚本响应。业务项目把第三方系统基础地址改为 `http://mock.company.internal/m/erp`，业务路径保持不变。

## 5. 完全离线部署

必须先在可联网、与目标 CPU 架构一致的 Linux Docker 构建环境完成镜像准备。Java JAR 不能代替 `docker save` 导出的镜像归档。

```sh
sh scripts/package-offline.sh
```

脚本构建并导出 app、runner 两个业务镜像，输出 `release/mocklab-images-1.0.0.tar` 和 SHA-256 文件。若同名包已经存在，脚本拒绝覆盖。

将以下内容复制到内网服务器：

- 镜像 tar 与 SHA-256 文件
- compose.yml
- deploy/ 全部配置
- scripts/ 与 docs/
- 前端构建产物 dist/（放入现有 Nginx webroot）
- 按内网环境单独准备的 `.env`

在内网服务器：

```sh
cd /opt/mocklab
sha256sum -c release/mocklab-images-1.0.0.sha256
docker load -i release/mocklab-images-1.0.0.tar
docker compose config --quiet
docker compose up -d --no-build --pull never
```

将 dist 放入现有 Nginx webroot 后验证管理页面、原样接口和脚本接口。不要在离线服务器上运行 `--build` 或 npm/Maven 下载命令。

## 6. 配置和资源

- 前端静态资源由现有 Nginx webroot 提供；更新前端时重新构建 dist 并同步到 Nginx webroot
- 数据库直接连接现有 MySQL 5.7；DB_URL、DB_USER、DB_PASSWORD 配置应用连接，不创建或修改数据库账号
- APP_BIND、APP_PORT 控制 app 容器的宿主机发布地址，容器内部固定 8080，现有 Nginx 代理该宿主地址
- 脚本容器 network_mode 为 none，仅通过共享 Unix Socket 与后端通信
- runner 与 app 使用 10001:10001，Socket 卷首次创建继承 runner 镜像内目录权限
- 如果使用已有自建卷导致 Socket 权限错误，应先检查属主和挂载路径，再仅修正该运行目录的权限，不要将其改为全局 777
- app 容器内存上限 1 GiB，runner 2 GiB；根据真实负载与服务器余量调整
- runner JVM 区域上限与容器总内存是不同层次，不声称每个工作进程 RSS 被精确限制为 256 MiB
- 默认脚本执行 1 秒，前后端及监督进程的超时值需要同时维护，反向代理读超时必须大于最大排队、脚本时间及人工延迟之和

检查隔离和资源配置：

```sh
docker inspect --format '{{.HostConfig.NetworkMode}}' "$(docker compose ps -q runner)"
docker inspect --format '{{.HostConfig.Memory}}' "$(docker compose ps -q runner)"
docker stats --no-stream
```

第一条必须为 none。不要给 app 挂载宿主 Docker Socket，也不要给 runner 挂载业务目录、数据库凭证或宿主文件系统。

## 7. 备份

MySQL 备份与恢复使用已有数据库的运维流程，不由业务 Compose 管理。

备份目标数据库中的系统配置、接口草稿、发布历史、操作记录和必要调用记录，并保留 .env、compose.yml、当前业务镜像版本及现有 Nginx 的前端目录与代理配置。前端 dist 更新需同步备份到 Nginx webroot 对应目录。

## 8. 恢复到独立验证环境

由 DBA 将备份恢复到独立测试数据库，再在项目副本的 .env 中设置测试库 DB_URL、DB_USER、DB_PASSWORD。已有表结构时使用 DB_INIT_MODE=never，配置不同 APP_PORT，再通过测试环境的现有 Nginx 入口访问页面。

```sh
docker compose -p mocklab-restore up -d --no-build --pull never
```

新项目名隔离 runner Socket 卷，不会自动创建新的数据库。检查系统数量、草稿、发布历史，实际调用原样和脚本接口，并验证回滚。入口切换和数据库恢复均沿用现有运维流程。

## 9. 升级与回退

升级前先备份数据库、配置及旧镜像，记录当前镜像 ID。为新版本使用独立镜像标签，更新 Compose 后执行启动和烟测；验证通过前保留旧产物。

当前 1.0.0 只提供初始建表脚本。后续涉及表结构变化时必须先审阅该版本数据库迁移脚本，并确认与旧应用的兼容性。应用回退可以切回旧镜像；不兼容的数据库变更不能仅通过回退镜像解决，必要时使用已验证的数据库备份恢复。

`docker compose down` 仅停止项目 app 和 runner，不管理外部 MySQL 或 Nginx。保留 runner Socket 卷即可，部署操作不需要清理数据库或业务文件。

## 10. 常见问题

| 现象 | 排查 |
| --- | --- |
| 页面复制出的地址不正确 | 开发检查 frontend/.env.development 的 VITE_BACKEND_URL；生产默认使用当前浏览器入口，固定地址时需修改 frontend/.env.production 并重新构建 dist |
| 页面是旧版本 | 检查 Nginx webroot 是否同步了最新 dist，以及浏览器缓存 |
| 静态资源 404 | 检查 Nginx `root` 是否指向 dist 所在目录，文件是否复制到该目录 |
| /api 或 /m/ 502 | 检查 app 是否启动、APP_BIND/APP_PORT 是否正确、Nginx proxy_pass 是否可达 |
| Mock 地址返回 404 | 检查系统/接口启停、归档、是否发布、系统标识、大小写、末尾斜杠 |
| 方法返回 405 | 检查方法；静态路径不会回退到宽泛参数路径 |
| 原样响应正常，脚本返回 503 | 查看 runner 健康、Unix Socket 挂载和属主，检查队列是否拥塞 |
| 脚本返回 504 | 减少计算、排查死循环，先在线调试 |
| 调试正文格式错误 | Content-Type 与正文格式需要一致，文本/XML 使用 rawBody |
| 管理入口返回 403 | 检查现有 Nginx 的管理入口访问策略及请求标记 |
| 日志正文没有保存 | 默认关闭；如需诊断设置 LOG_BODY=true，仍会脱敏和截断 |
| 来源地址总是网关地址 | 默认只记录后端观测地址，没有信任任意代理头 |

## 11. 部署后检查

- `docker compose ps` 中 runner 健康、app 持续运行，没有反复重启
- 后端 `/actuator/health` 返回 UP，Nginx 页面、管理接口和实际 Mock 调用正常
- 实际调用 JavaScript 接口，确认 Unix Socket 通信、脚本执行和超时处理正常
- 核对 runner 无网络及资源配额配置，按实际负载验证稳定性
- 验证数据库备份恢复，并保留可回退的镜像、配置和前端文件

本机编译或单元测试不能替代目标服务器的部署验证。
