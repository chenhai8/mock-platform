# MockLab Linux Docker 部署教程

本文只部署业务项目 app 和 runner。数据库使用现有 MySQL 5.7，反向代理使用现有 Nginx，不启动数据库或 Nginx 容器，不需要 DB_ROOT_PASSWORD。前端在构建时打包进 backend JAR，无需独立前端运行服务。

## 1. 部署形态

```text
使用者 / 业务服务器 -> 现有 Nginx -> 宿主机 16080 -> app:8080 -> 现有 MySQL 5.7
                                                         -> Unix Socket -> runner
```

- Compose 只创建 app、runner 及两者共用的 runner-socket 卷，不创建数据库数据卷
- app 提供前端静态页面、/api 管理接口和 /m/ Mock 入口
- 默认宿主机 127.0.0.1:16080 只供同机 Nginx 代理；远程代理时使用业务服务器的内网 IP 绑定
- runner 不暴露网络端口，通过 Unix Socket 与 app 通信
- 管理入口沿用现有 Nginx 的内网访问策略；如果需要只开放 Mock 调用，单独代理 /m/ 路径
- HTTPS 由现有 Nginx 处理，应用容器内保持 HTTP

## 2. 服务器准备

建议先用 x86_64 Linux、4 核、8 GiB 内存和至少 10 GiB 可用磁盘验证。安装 Docker Engine 与 Compose v2 插件。目标是 ARM64 时，联网构建机器也要构建对应平台镜像，不能直接复制 x86 镜像使用。

```sh
docker version
docker compose version
```

将项目放到例如 `/opt/mocklab`，所有命令都在项目根目录执行。不要在原型 prototype 目录启动正式部署。

```sh
cd /opt/mocklab
# 仅在尚无 .env 时创建；已有配置直接编辑，不覆盖
if [ ! -e .env ]; then cp deploy/env.example .env; fi
chmod 600 .env
```

编辑 `.env`：

```dotenv
DB_URL=jdbc:mysql://192.168.10.30:3306/mocklab?useUnicode=true&characterEncoding=UTF-8&serverTimezone=UTC&useSSL=false
DB_USER=填写已有数据库账号
DB_PASSWORD=填写已有数据库密码
DB_INIT_MODE=always
MOCK_BASE_URL=http://mock.company.internal
APP_BIND=127.0.0.1
APP_PORT=16080
LOG_DAYS=7
LOG_MAX_ROWS=1000000
LOG_BODY=false
```

DB_URL 指向已有数据库；容器内 127.0.0.1 是 app 自身，不能将其作为宿主数据库地址。请 DBA 提供独立库和应用账号，账号授权沿用现有数据库管理流程。库不存在时可由 DBA 执行 deploy/init-mysql.sql。

DB_INIT_MODE=always 会在启动时执行 schema.sql 创建缺失的表，需 CREATE、REFERENCES 权限。如果 DBA 已手动执行建表脚本，设置为 never，应用仅需正常读写权限。

MOCK_BASE_URL 填写业务调用方实际访问的已有 Nginx 地址。密码不提交到 Git；包含 dotenv 特殊字符时按 .env 语法正确引用。

### 接入已有 Nginx

在现有站点 server 内按实际部署情况配置 location，同机示例：

```nginx
location / {
    proxy_pass http://127.0.0.1:16080;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    client_max_body_size 5m;
    proxy_read_timeout 25s;
}
```

此配置同时代理页面、/api、/m/ 和健康检查，保留原始路径。推荐使用独立域名根路径接入。若仅提供 Mock 入口，将该代理放在 location /m/ 中，管理页面由已有的受限站点代理。

Nginx 与业务容器不在同一台机器时，将 APP_BIND 改为业务宿主机内网 IP，proxy_pass 指向该 IP:16080，并沿用公司现有访问控制规则。修改 APP_PORT 时同步修改代理目标。

deploy/nginx.conf 已调整为可合并到现有站点 server 内的 location 参考片段，不是完整 Nginx 主配置。admin-allow.conf 仅为可选的网段参考，是否合并及允许范围由现有站点维护者决定。两者均不被业务 Compose 挂载，不覆盖服务器现有配置。deploy 目录各文件用途见 [部署文件说明](../deploy/README.md)。

## 3. 联网构建与启动

```sh
docker compose config --quiet
docker compose build
docker compose up -d
docker compose ps
```

首次构建需要下载公共基础镜像、Maven 与 npm 依赖。运行阶段不访问这些仓库。执行服务要预热 4 个进程，首次就绪可能需要几十秒；后端等待 runner 健康后启动，再连接已有数据库；数据库地址和授权需要预先可用。

```sh
curl -f http://127.0.0.1:16080/actuator/health
docker compose logs --tail=100 app runner
```

健康结果应为 `{"status":"UP"}`。浏览器打开管理入口，创建第三方系统和接口，调试并发布。

## 4. 第一次真实调用

假设创建系统标识 `erp`，接口为 POST `/api/orders/query`，发布原样响应 `{"code":"0000","message":"成功"}`：

```sh
curl -i 'http://mock.company.internal/m/erp/api/orders/query' \
  -H 'Content-Type: application/json' \
  --data '{"orderId":"1001"}'
```

返回 HTTP 200，正文就是保存的文本。之后改为 JavaScript：

```javascript
function main(request, mock) {
  return {
    status: 200,
    body: {
      code: "0000",
      orderId: request.body.orderId,
      requestId: mock.uuid()
    }
  };
}
```

保存草稿后真实调用保持旧响应，重新发布后才切换到脚本响应。业务项目把第三方系统基础地址改为 `http://mock.company.internal/m/erp`，业务路径保持不变。

## 5. 完全离线部署

必须先在可联网、与目标 CPU 架构一致的 Linux Docker 构建环境完成镜像准备。当前本机交付的 release 目录是 Java 运行产物，不等于 Docker 镜像包。

```sh
sh scripts/package-offline.sh
```

脚本仅构建并导出 app、runner 两个业务镜像，不拉取 MySQL 或 Nginx 镜像，输出 `release/mocklab-images-1.0.0.tar` 和 SHA-256 文件。若同名包已经存在，脚本拒绝覆盖。

将以下内容复制到内网服务器：

- 镜像 tar 与 SHA-256 文件
- compose.yml
- deploy/ 全部配置
- scripts/ 与 docs/
- 按内网环境单独准备的 `.env`

在内网服务器：

```sh
cd /opt/mocklab
sha256sum -c release/mocklab-images-1.0.0.sha256
docker load -i release/mocklab-images-1.0.0.tar
docker compose config --quiet
docker compose up -d --no-build --pull never
```

断开公网后验证管理页面、原样接口和脚本接口。不要在离线服务器上运行 `--build` 或 npm/Maven 下载命令。

## 6. 配置和资源

- 改变 MOCK_BASE_URL 后重新创建 app：`docker compose up -d --no-deps app`
- 数据库直接连接现有 MySQL 5.7；DB_URL、DB_USER、DB_PASSWORD 配置应用连接，不创建或修改数据库账号
- APP_BIND、APP_PORT 仅控制 app 的宿主机发布地址；容器内部固定 8080，现有 Nginx 代理该宿主机地址
- 脚本容器 network_mode 为 none，仅通过共享 Unix Socket 与后端通信
- runner 与 app 使用 10001:10001，Socket 卷首次创建继承 runner 镜像内目录权限
- 如果使用已有自建卷导致 Socket 权限错误，应先检查属主和挂载路径，再仅修正该运行目录的权限，不要将其改为全局 777
- app 容器内存上限 1 GiB，runner 2 GiB；根据真实负载与服务器余量调整
- runner JVM 区域上限与容器总内存是不同层次，不声称每个工作进程 RSS 被精确限制为 256 MiB
- 默认脚本执行 1 秒，前后端及监督进程的超时值需要同时维护，反向代理读超时必须大于最大排队、脚本时间及人工延迟之和

检查隔离和资源配置：

```sh
docker inspect --format '{{.HostConfig.NetworkMode}}' "$(docker compose ps -q runner)"
docker inspect --format '{{.HostConfig.Memory}}' "$(docker compose ps -q runner)"
docker stats --no-stream
```

第一条必须为 none。不要给 app 挂载宿主 Docker Socket，也不要给 runner 挂载业务目录、数据库凭证或宿主文件系统。

## 7. 备份

MySQL 备份与恢复使用已有数据库的运维流程，不由业务 Compose 管理。不执行 scripts/backup.sh，该文件是历史 db 容器备份脚本。

备份目标数据库中的系统配置、接口草稿、发布历史、操作记录和必要调用记录，并保留 .env、compose.yml、当前业务镜像版本及现有 Nginx 的代理配置。.env 含凭据，存放在公司批准的受限位置。

## 8. 恢复到独立验证环境

由 DBA 将备份恢复到独立测试数据库，再在项目副本的 .env 中设置测试库 DB_URL、DB_USER、DB_PASSWORD。已有表结构时使用 DB_INIT_MODE=never，配置不同 APP_PORT 和测试入口 MOCK_BASE_URL。

```sh
docker compose -p mocklab-restore up -d --no-build --pull never
```

新项目名隔离 runner Socket 卷，不会自动创建新的数据库。检查系统数量、草稿、发布历史，实际调用原样和脚本接口，并验证回滚。入口切换和数据库恢复均沿用现有运维流程。

## 9. 升级与回退

升级前先备份数据库、配置及旧镜像，记录当前镜像 ID。为新版本使用独立镜像标签，更新 Compose 后执行启动和烟测；验证通过前保留旧产物。

当前 1.0.0 只提供初始建表脚本。后续涉及表结构变化时必须先审阅该版本数据库迁移脚本，并确认与旧应用的兼容性。应用回退可以切回旧镜像；不兼容的数据库变更不能仅通过回退镜像解决，必要时使用已验证的数据库备份恢复。

`docker compose down` 仅停止项目 app 和 runner，不管理外部 MySQL 或 Nginx。保留 runner Socket 卷即可，部署操作不需要清理数据库或业务文件。

## 10. 常见问题

| 现象 | 排查 |
| --- | --- |
| 页面复制出的地址是 localhost | 设置真实 MOCK_BASE_URL，重建 app |
| Mock 地址返回 404 | 检查系统/接口启停、归档、是否发布、系统标识、大小写、末尾斜杠 |
| 方法返回 405 | 检查方法；静态路径不会回退到宽泛参数路径 |
| 原样响应正常，脚本返回 503 | 查看 runner 健康、Unix Socket 挂载和属主，检查队列是否拥塞 |
| 脚本返回 504 | 减少计算、排查死循环，先在线调试 |
| 调试正文格式错误 | Content-Type 与正文格式需要一致，文本/XML 使用 rawBody |
| 管理入口返回 403 | 检查现有 Nginx 的管理入口访问策略及请求标记 |
| 日志正文没有保存 | 默认关闭；如需诊断设置 LOG_BODY=true，仍会脱敏和截断 |
| 来源地址总是网关地址 | 默认只记录后端观测地址，没有信任任意代理头 |

## 11. 本次验证范围

本机 Windows + JDK 21 已完成编译、自动化契约测试、真实 HTTP 测试及页面体验。当前机器没有 Docker，因此 Linux 镜像构建、现有 MySQL 连接、Unix Socket 容器通信、容器资源配额以及现有 Nginx 代理还需在目标服务器执行本文步骤验证。不能将本机成功等同于 Docker 部署已验收。
